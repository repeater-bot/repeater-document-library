# Grill Me — 深度审问协议

## 何时使用

- 用户提出一个计划、设计、架构方案或产品思路
- 用户说"帮我审一下"、"grill me"、"拷问我"、"challenge my thinking"
- 在开始编码/实施之前，需要确保双方对需求有共同理解
- 怀疑用户可能没有想清楚某些边界情况

## 核心原则

1. ** relentlessly（不留情面）**：每个方面都要问到，不因为"看起来 obvious"就跳过
2. **决策树遍历**：按分支逐个深入，先解决当前分支的依赖，再进入下一个分支
3. **一次只问一个问题**：同时抛多个问题会让人不知所措
4. **事实 vs 决策**：
   - **事实**（能从代码库、文件、工具中查到的）→ 自己查，不要问用户
   - **决策**（需要用户拍板的）→ 逐个抛给用户，等回答
5. **每题附带推荐答案**：不要只抛问题，要给出"如果是我，我会怎么做"的建议
6. **达成共识前不行动**：直到用户明确确认"我们达成一致了"，才开始执行任何操作

## 执行流程

### Step 1: 开场确认

用一句话确认用户想要被审问的主题：

> "好的，我来对你关于 **[主题]** 的计划进行深度审问。我会逐条追问，每条只问一个问题。如果你同意，我们就开始。"

### Step 2: 逐分支审问

按以下维度（或根据主题自定义维度）逐个分支深入：

| 维度 | 典型问题 |
|------|---------|
| **目标** | 这件事成功的标准是什么？如何衡量？ |
| **范围** | 包含什么？明确不包含什么？ |
| **用户/受众** | 谁用？他们的核心痛点是什么？ |
| **依赖** | 这件事依赖哪些前置条件？哪些团队/系统？ |
| **风险** | 最可能在哪里失败？Plan B 是什么？ |
| **边界情况** | 极端输入、空状态、错误路径怎么处理？ |
| **优先级** | 如果只能做一半，先做哪一半？ |
| **验收** | 怎么证明这件事做完了且做对了？ |

### Step 3: 每题格式

每个问题按以下格式输出：

```
**问题 N: [一句话概括问题]**

[具体展开，说明为什么这个问题重要，当前方案在这个点上是否模糊]

💡 **我的建议**: [给出你的推荐答案，基于工程经验和上下文]

请回答后我继续下一个问题。
```

### Step 4: 循环直到穷尽

- 用户回答后，根据答案判断是否需要追问（"你提到了 X，那 Y 呢？"）
- 当前分支穷尽后，进入下一个分支
- 所有分支走完后，做一次总结确认

### Step 5: 总结确认

输出一份共识摘要：

```
## 共识摘要

我们已就以下要点达成一致：
1. ...
2. ...
3. ...

**待决策项**（如有）：
- ...

请确认以上理解是否正确。确认后我们可以进入执行阶段。
```

## 注意事项

- ❌ **不要一次问多个问题**
- ❌ **不要替用户做决定**（可以给建议，但必须等用户确认）
- ❌ **不要在达成共识前开始写代码/改文件**
- ✅ **如果相关事实存在于代码库中，先读取代码/文档再提问**
- ✅ **保持礼貌但坚定** — "不留情面"指的是对问题的深度，不是态度粗暴

## 使用示例

**用户**: "我想重构这个登录模块"

**AI**: "好的，我来对你关于'重构登录模块'的计划进行深度审问。我会逐条追问，每条只问一个问题。如果你同意，我们就开始。

**问题 1: 重构的触发原因是什么？**

当前登录模块具体遇到了什么问题？是性能瓶颈、代码难以维护、安全漏洞，还是功能无法满足新需求？明确原因才能确定重构的范围和成功标准。

💡 **我的建议**: 如果是代码难以维护，建议先列出当前最痛的 3 个具体代码坏味道（如重复逻辑、过长函数、紧耦合），作为重构的验收指标。

请回答后我继续下一个问题。"
